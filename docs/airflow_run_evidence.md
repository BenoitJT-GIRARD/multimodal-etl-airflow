# Evidence of a DAG run in Apache Airflow

Captured logs of the `multimodal_etl` DAG.

Environment: Apache Airflow 2.10.4, `LocalExecutor`, PostgreSQL metadata database, image
built from `docker/Dockerfile`, empty database at the start. The full procedure is in
`docs/airflow_runbook.md`.

These transcripts are **captures**. The progress lines Airflow prints are kept, the debug
lines are dropped, and nothing is rewritten by hand: the file is regenerated by running the
DAG again.

## 3. One task replayed on its own

This is the point that justifies the orchestration: any task has to be replayable
independently of the others. The working area has just been emptied by `cleanup`, so
`transform` no longer has its input file.

```
$ airflow tasks test multimodal_etl transform 2026-09-03
```

```
airflow.task              | Executing <Task(PythonOperator): transform> on 2026-09-03
multimodal_etl.pipeline   | === STEP 2 — TRANSFORM ===
multimodal_etl.transit    | Working area: 'extraction.json' missing, falling back to archive raw_publications_20260903_074655.json
multimodal_etl.transform  | Transform: 164 raw publications read
multimodal_etl.transform  | Transform: 123/164 publications valid after cleaning
multimodal_etl.transform  | Transform: dataset of 123 rows exported to data/processed/publications_20260903_074658.parquet
multimodal_etl.transit    | Working area: 'dataset.parquet' staged for the next step
Marking task as SUCCESS. task_id=transform
```

The task noticed its working file was gone, fell back to the last archived extraction, and
finished successfully — **without replaying the extraction**, which takes a minute and
spends an API call.

## 4. The load cannot duplicate a row

A second run does not reload what is already there:

```
$ airflow dags test multimodal_etl 2026-09-03
```

```
multimodal_etl.extract    | Extract: 164 raw publications in total
multimodal_etl.images     | Images: 125 downloaded, 4 failures, 35 skipped (10.3 MB on disk)
multimodal_etl.transform  | Transform: 123/164 publications valid after cleaning
multimodal_etl.load       | Load: 2 rows added to 'publication'
multimodal_etl.load       | Load: table 'source' already up to date
multimodal_etl.load       | Load: 2 rows added to 'text_content'
multimodal_etl.load       | Load: 2 rows added to 'image_content'
multimodal_etl.load       | Load: table 'label' already up to date
multimodal_etl.load       | Load: 2 rows added to 'publications'
multimodal_etl.load       | Load: 2 new publications, 121 already present
DagRun Finished: state=success
```

Of the 123 publications the second run kept, 121 were already in the database and 2 were
new — the articles the feeds published in the sixty seconds between the two runs. Neither
the `source` table nor the `label` table moved: the same five sources, and the two new
articles carry no ground-truth label.

**Where the guarantee lives.** Not in this loop. Every table is declared with its primary
key and the insert skips conflicts, so a duplicate is refused by the **database** rather
than avoided by the code. The count of rows written is measured before and after the
insert, not predicted. An earlier version read the existing keys and then wrote the rest,
which was a race by construction — in a pipeline whose whole argument is that its tasks can
be replayed.

A unit test issues its own `INSERT`, bypassing the loader entirely, and checks the database
raises `IntegrityError`.
